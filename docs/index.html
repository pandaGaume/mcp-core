01 — Motivation

The official SDK is not enough when…

  1. Multiple LLM clients need different tool descriptions on the same server — Claude wants concise, an internal tool prefers verbose.
  2. The set of live resources changes while sessions are open — objects added, renamed, removed — and the agent must be notified.
  3. The same tool catalog must run against different backends — a 3D engine, a geo viewer, a node graph, a test mock.
  4. A tool exists conceptually but is not supported on this instance — you want the client to never see it instead of getting an error.
  5. Agents need to rewrite their own tool descriptions mid-session — and persist that across reconnects.
@cyanmycelium/mcp-core is the abstraction stack that makes those concerns first-class instead of bolt-ons. It is engine-neutral, runtime-agnostic, and has been used in production behind a multi-backend MCP server.

04 — Quick start

A minimal MCP server in four steps

A behavior owns the schemas, an adapter owns the execution. The server wires them together with a transport.

TypeScript · server.ts 
// 1. State — a serializable snapshot of what the client can read.
interface CounterState {
  value: number
}

// 2. Adapter — binds the behavior to a real backend.
class CounterAdapter extends McpAdapterBase<CounterState> {
  private state: CounterState = { value: 0 }

  read(): CounterState {
    return { ...this.state }
  }

  async increment(by: number = 1): Promise<CounterState> {
    this.state.value += by
    this.emitResourceContentChanged('app://counter')
    return this.read()
  }

  async reset(): Promise<CounterState> {
    this.state.value = 0
    this.emitResourceContentChanged('app://counter')
    return this.read()
  }
}

// 3. Behavior — declares the MCP-side contract.
class CounterBehavior extends McpBehavior<CounterState, CounterAdapter> {
  namespace = 'counter'
  uriTemplate = 'app://counter'

  tools() {
    return [
      {
        name: 'counter_increment',
        description: 'Increment the counter by a given amount.',
        inputSchema: {
          type: 'object',
          properties: { by: { type: 'number', default: 1 } },
        },
        handler: (args, adapter) => adapter.increment(args.by),
      },
      {
        name: 'counter_reset',
        description: 'Reset the counter to zero.',
        inputSchema: { type: 'object' },
        handler: (_, adapter) => adapter.reset(),
      },
    ]
  }
}

// 4. Wire them up and start.
const server = new McpServerBuilder()
  .withBehavior(new CounterBehavior(new CounterAdapter()))
  .withTransport(new StdioTransport())
  .build()

await server.start()

Save as server.ts, build, run with node server.js. Any MCP client (Claude Desktop, an SDK, a hand-rolled JSON-RPC over stdio) can now call counter_increment and counter_reset and read app://counter.

05 — Grammar

Per-client tool descriptions, no conditional code

A grammar is a set of description overrides that the server applies on top of the behavior’s baseline schemas before sending them to the client.

5.1Static grammars selected per client

TypeScript 
import { McpGrammar } from '@cyanmycelium/mcp-core'

const claude = McpGrammar.fromJSON({
  counter_increment: { description: 'Add N to counter.' },
  counter_reset:     { description: 'Zero the counter.' },
})

const verbose = McpGrammar.fromJSON({
  counter_increment: {
    description:
      'Increase the persistent counter value. Accepts a numeric `by` '
      + 'argument; defaults to 1. Emits a resource change event so the '
      + 'client can re-read app://counter.',
  },
})

const server = new McpServerBuilder()
  .withBehavior(new CounterBehavior(new CounterAdapter()))
  .withGrammarResolver((clientInfo) =>
    clientInfo.name === 'claude-desktop' ? 'concise' : 'verbose'
  )
  .withGrammars({ concise: claude, verbose })
  .build()

Claude sees the short description, every other client sees the long one. No conditional code in the behavior.

5.2Runtime mutation by the agent itself

McpGrammarBehavior exposes the grammar store as a regular MCP behavior with six tools (grammar_list, grammar_read, grammar_set, grammar_delete, grammar_import, grammar_export). The agent can rewrite its own tool descriptions during a session, and the server emits notifications/tools/list_changed so clients re-fetch the updated schemas.

TypeScript 
import {
  McpGrammarStore,
  McpGrammarBehavior,
} from '@cyanmycelium/mcp-core'

const store = new McpGrammarStore({
  initial: JSON.parse(await readFile('grammars.json', 'utf8')),
})

const server = new McpServerBuilder()
  .withBehavior(new CounterBehavior(new CounterAdapter()))
  .withBehavior(new McpGrammarBehavior(store))
  .withGrammarStore(store)
  .build()

store.on('change', async () => {
  await writeFile('grammars.json', JSON.stringify(store.toJSON(), null, 2))
})

Persist store.toJSON() to disk between runs to keep agent-authored descriptions across restarts.

06 — Capability filtering

Advertise only what a resource can actually do

The adapter declares which tools apply to which resource types. The behavior filters tools accordingly before advertising them.

TypeScript 
import { McpAdapterBase, ToolSupport } from '@cyanmycelium/mcp-core'

class CameraAdapter extends McpAdapterBase<CameraState> {
  constructor(private camera: Camera) { super() }

  getToolSupport(tool: string): ToolSupport {
    switch (tool) {
      case 'camera_orbit':
        return this.camera.type === 'arcRotate'
          ? ToolSupport.Full
          : ToolSupport.None
      case 'camera_set_fov':
        return ('fov' in this.camera)
          ? ToolSupport.Full
          : ToolSupport.None
      case 'camera_look_at':
        return ToolSupport.Full
      default:
        return ToolSupport.None
    }
  }
}

The client never sees tools it cannot actually call. No error spam.

07 — Portability

Write the schema once, run it everywhere

The behavior owns the schemas. The adapter owns the execution. Any adapter that satisfies the contract can be paired with the same behavior.

TypeScript 
// In-memory: tests & local dev.
class InMemoryCounterAdapter extends McpAdapterBase<CounterState> {
  private value = 0
  read() { return { value: this.value } }
  async increment(by = 1) { this.value += by; return this.read() }
}

// Redis: distributed.
class RedisCounterAdapter extends McpAdapterBase<CounterState> {
  constructor(private redis: Redis, private key = 'counter') { super() }
  async read() {
    return { value: Number(await this.redis.get(this.key)) || 0 }
  }
  async increment(by = 1) {
    const value = await this.redis.incrby(this.key, by)
    this.emitResourceContentChanged('app://counter')
    return { value }
  }
}

// Postgres: durable, single source of truth.
class DbCounterAdapter extends McpAdapterBase<CounterState> {
  constructor(private db: Pool) { super() }
  async read() {
    const { rows } = await this.db.query('SELECT value FROM counter WHERE id = 1')
    return { value: rows[0]?.value ?? 0 }
  }
}

// Same behavior, any adapter.
const behavior = new CounterBehavior(new RedisCounterAdapter(redis))

The pattern scales to richer domains: a single behavior describing mesh operations can run against a BabylonJS scene, a Cesium viewer, or an in-memory fixture, with the LLM-facing schemas never changing.

08 — Transports

Transports

Transport Module Use case
DirectTransport @cyanmycelium/mcp-core/server One server, one WebSocket. The default.
MultiplexTransport @cyanmycelium/mcp-core/server Multiple servers sharing one WebSocket via envelope routing.
LoopbackTransport @cyanmycelium/mcp-core/server Server and client in the same process. Tests, local dev, embedded use.
StdioTransport @cyanmycelium/mcp-core/node Line-delimited JSON-RPC over stdin / stdout. The MCP standard for CLI agents.

Implement IMessageTransport for anything else (WebRTC, postMessage, gRPC).

Nota. Runs in both Node.js and the browser. In the browser the server connects to an MCP broker over WebSocket; the broker relays JSON-RPC frames to and from the actual MCP client.
